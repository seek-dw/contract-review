## 一、系统定位与边界

**定位**：面向企业合同审批场景的**辅助审查工具**。系统拉取待审合同、解析内容、执行规则审查、
生成风险意见并写回审批评论区，**不代替人工审批**，不产生"通过/驳回"的终局决定。

**边界（原文 2.4.1）**：

| 能力域 | 系统做什么 | 系统不做什么 |
| --- | --- | --- |
| 接入 | 拉取待办、拉取详情、下载附件、按业务唯一标识去重 | 不创建审批单、不修改审批单业务字段 |
| 审查 | 解析文档、OCR 扫描件、规则匹配、风险汇总 | 不训练/不调用大模型做终局判断；不代替法务签字 |
| 输出 | 结果入库、生成回写文本、写入评论区、全链路日志 | 不修改合同原文、不删除审批记录 |

**关键设计取舍**：

1. **规则与解析分离**。解析只负责"把文档变成结构化字段 + 原文位置"，规则只负责"拿字段和
   原文做判断"。二者通过 `ParseOutcome` 数据结构解耦，规则可单独测试，解析可单独替换引擎。
2. **金额、日期、比例全部由确定性代码处理**（正则 + 数值解析），不做语义猜测；语义类结论
   （如"保密条款缺失"）只输出"未检出"并保留检索依据，最终判断权交给人。
3. **审批系统通过网关接口接入**。`ApprovalGateway` 抽象出 4 个外部动作，本地提供
   `MockApprovalGateway`（读写 JSON 文件，模拟 OA 状态）与 `HttpApprovalGateway`（真实 OA），
   由配置切换，二者行为契约完全一致，演示链路使用 mock。

## 四、关键流程

### 4.1 拉取与去重

```
list_pending_contract_approvals(limit)
  → gateway.list_pending(limit)            外部系统
  → 按 approval_code 查 approval_tasks
      ├─ 不存在：INSERT，task_status=pending
      └─ 已存在：UPDATE 标题/申请人/申请时间/附件数，保留 task_status 与 write_status
  → 返回 created / updated 计数（演示去重证据）
```

去重键：`approval_tasks.approval_code` 上建唯一索引，数据库层兜底并发重复写入。

### 4.2 下载附件

```
download_contract_attachment(instance_id, attachment_id, file_name)
  → gateway.download_attachment()           外部系统（超时/404 → blocked）
  → 落盘 data/attachments/{approval_code}/{attachment_id}_{safe_name}
  → 计算 SHA256，写 approval_attachments（download_status=success）
  → 返回 document_id(=attachment.id) / local_path / sha256 / size
```

**路径安全**：文件名只保留 basename 并过滤路径分隔符与 `..`，最终路径必须落在
`attachment_dir` 之下，否则拒绝（这是必要校验，不是冗余防御）。

### 4.3 解析

```
parse_contract_document(document_id)
  → 按扩展名选择 reader：pdf / docx / 图片
  → PDF：逐页取文本层；字符数 < 阈值 → 该页判为扫描页 → 渲染 200DPI → OCR
  → 拼接全文本 + 每行带 (page, line_no) 位置
  → 全文有效字符 < 阈值 → DocumentEmptyError → blocked
  → 字段抽取（8 项）+ 条款抽取（8 类），每项带 FieldEvidence
  → 写 contract_parses（parse_status / parse_error / parse_meta_json）
```

**OCR 失败判定**：引擎抛错，或全部文本块置信度低于阈值，或识别结果有效字符不足，
都抛 `OcrUnavailableError` → `blocked`，`parse_error` 写明页码与原因。

### 4.4 规则审查

```
run_contract_rules(case_id)
  → 载入 task + 最新 contract_parses + 启用中的 review_rules（按 priority 升序）
  → 对每条规则求值：
      match_mode = keyword      → 关键词/正则是否出现在指定条款或全文
      match_mode = missing      → 指定字段是否提取成功且非空（缺失即命中）
      match_mode = threshold    → 从条款原文抽数值，与 match_text 中的阈值比较
  → 命中 → 写 rule_hits（含规则快照字段）
  → 汇总：命中最高风险等级 → overall_risk_level
  → 生成 focus_points（去重后的关注点）
  → task_status → reviewing
```

**风险汇总规则**：取所有命中规则中最高的风险等级；无命中为 `low`。

### 4.5 结果保存与回写

```
save_review_result(case_id, overall_risk_level, summary_text, focus_points_json, comment_text)
  → 写 review_results，返回 review_id

write_approval_comment(instance_id, review_id)
  → task.write_status: not_written → writing（条件更新，防并发重复写）
  → gateway.write_comment()                   超时/异常 → failed + blocked
  → 成功 → success，写 comment_logs
```

**幂等**：`write_status=success` 的任务再次调用直接返回上次结果，不重复写外部系统；
`writing` 状态说明有并发写在进行，返回冲突提示。

### 4.6 阻塞与重试

| 阻塞原因 | 异常 | 重试入口状态 |
| --- | --- | --- |
| 附件缺失/下载失败 | `AttachmentMissingError` | `parsing` |
| 图片无法识别 | `OcrUnavailableError` | `parsing` |
| 文档内容为空 | `DocumentEmptyError` | `parsing` |
| 审批接口调用失败 | `ApprovalGatewayError` | 按失败发生阶段 |
| 回写超时/失败 | `CommentWriteError` | `reviewing` |

`retry_blocked_task(task_id)`：校验当前必须是 `blocked`，清空 `parse_error`，按 `retry_target`
回到 `parsing`（重新解析）或 `reviewing`（重新审查 + 回写）。

## 五、数据模型补充说明

原文 2.4.9 给出的是**最小字段集**，实现中为满足 2.4.3/2.4.4/2.4.6 的可追溯要求补充了
少量字段，全部在 `models.py` 注释中标注「扩展」并说明原因：

| 表 | 扩展字段 | 原因 |
| --- | --- | --- |
| `approval_tasks` | `applied_at`、`attachment_count`、`blocked_reason`、`retry_target` | 2.4.3 要求待办返回申请时间与附件数量；2.4.4 要求记录阻塞原因与重试目标 |
| `approval_attachments` | `external_attachment_id`、`checksum`、`file_size`、`download_error` | 2.4.3 要求返回校验信息；外部附件编号用于重下 |
| `contract_parses` | `parse_meta_json` | 记录 OCR 页数、页数、耗时，便于排查 |
| `rule_hits` | `rule_code_snapshot`、`rule_name_snapshot`、`risk_level_snapshot`、`suggestion_snapshot` | 规则会被修改，命中记录必须保留"当时"的规则内容，否则回查失真 |
| `review_rules` | `priority`、`condition_json` | 同类规则需要优先级；threshold 型规则需要结构化阈值 |

## 六、技术栈与运行

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | Python 3.12 | 用户唯一熟悉的语言，且 3.12 生态轮子齐全 |
| Web | FastAPI + Uvicorn | 类型化、自带 OpenAPI，工具服务天然可暴露为 HTTP |
| ORM | SQLAlchemy 2.x | 显式模型定义，SQLite 零配置演示，可切 PostgreSQL |
| 数据库 | SQLite（演示）/ PostgreSQL（可切） | 通过 `CR_DB_URL` 切换 |
| PDF | PyMuPDF | 同时提供文本层与页面渲染，一套库覆盖两种模式 |
| DOCX | python-docx | 读取段落与表格 |
| OCR | RapidOCR (ONNXRuntime) | 纯 Python 部署、无需系统级 tesseract、中文合同识别可用 |
| 页面 | Jinja2 服务端渲染 | 调用端只是演示入口，避免引入前端构建链 |

**运行**（依赖管理用 uv）：

```bash
uv venv --python 3.12                          # 建虚拟环境并锁定 3.12
uv pip install -r requirements.txt             # 安装依赖

uv run --python 3.12 python scripts/init_db.py        # 建表 + 种子规则
uv run --python 3.12 python scripts/make_samples.py   # 生成示例合同（含扫描件）
uv run --python 3.12 python scripts/demo_flow.py      # 闭环演示
uv run --python 3.12 python -m uvicorn app.main:app --port 8080   # 调用端页面
uv run --python 3.12 python -m pytest -q              # 测试
```

选用 uv 的理由：

- **自带解释器管理**：`uv venv --python 3.12` 会在缺少 3.12 时自动下载，
  不要求用户在系统里预装特定版本，降低"我这边跑不起来"的概率；
- **`uv run` 免激活**：每次命令前自动定位项目 `.venv`，
  不会误用系统 Python，也不需要记得先 activate；
- **`--python 3.12` 是硬约束**：环境若被改成别的版本会直接报错而不是静默降级，
  保证复现的就是验证过的那套版本。
- **仍保持 pip 兼容**：依赖走 `requirements.txt` + `uv pip`，
  没有绑定 `pyproject.toml`，评审方若只想用原生 pip 也能装。

## 七、已知局限（不夸大）

1. 字段抽取基于正则与版式假设，**对排版差异大的合同需要补充模式**；抽取失败会如实标记
   `extract_status=failed` 并记录原因，不会伪造字段值。
2. OCR 依赖 RapidOCR 内置中文模型，**手写体、印章遮挡、低分辨率扫描件识别率会下降**；
   识别不足时进入 `blocked` 交人工，而不是猜。
3. `threshold` 型规则只处理能在原文定位到数值的情形（如"预付款比例 60%"），
   数值藏在表格图片里时依赖 OCR 文本质量。
4. 真实 OA 接入只提供 HTTP 网关骨架，**具体厂商字段映射需按对接文档补充**；演示链路
   使用 mock 网关，两者接口契约一致。
5. 未实现用户登录与权限体系 —— 原文 2.4 未要求，调用端定位为内网演示入口。
