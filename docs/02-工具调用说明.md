# 工具调用说明（需求 2.4.10）

本文档说明本系统对外暴露的 7 个工具函数的调用方式、参数语义、返回结构、
异常约定与典型调用链。面向**接入方**（审批系统 Agent、外部编排器）与**验收人**。

代码位置：`app/tools/contract_tools.py`
HTTP 映射：`app/main.py` 中 `/api/tools/*` 路由

---

## 零、ID 语义（先读这一节，避免传错参数）

系统里存在四类标识，含义不同，**不能混用**：

| 参数名 | 含义 | 来源 | 示例 |
| --- | --- | --- | --- |
| `instance_id` | 审批单**业务**唯一标识 | 审批系统 | `HT-2024-0001` |
| `case_id` | 本地任务主键 | 拉取后由系统生成 | `4` |
| `document_id` | 本地附件主键 | 下载工具返回 | `4` |
| `review_id` | 本地结果主键 | 保存工具返回 | `1` |

**为什么不统一成一个 ID**：
`instance_id` 属于外部系统，本系统无权定义；其余三个是本地主键。
若强行统一（例如都用 `instance_id`），则一个审批单多个附件时无法区分，
一个审批单多轮审查时也无法区分。因此保留四类标识，并在每个工具的参数名上写清楚。

**转换关系**：

```
instance_id ──(拉取)──→ case_id ──(下载)──→ document_id
                            └──(保存)──→ review_id
```

## 一、`list_pending_contract_approvals(limit)`

### 作用
从审批系统拉取待处理审批单，**按 `approval_code` 去重**保存到本地。

### 参数

| 参数 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- | --- |
| `limit` | int | 否 | 1—200，默认 20 | 单次最大拉取条数 |

### 返回

```json
{
  "created": 4,          // 本次新建任务数
  "updated": 0,          // 本次更新的已存在任务数
  "skipped": 0,          // 详情拉取失败而跳过的数量
  "total": 4,            // 本次拉取到的审批单总数
  "items": [
    {
      "approval_code": "HT-2024-0001",
      "approval_title": "数据治理平台采购合同",
      "applicant_name": "李静",
      "applied_at": "2026-10-22T09:15:00",
      "attachment_count": 2,
      "action": "created",        // created | updated | detail_failed
      "task_status": "pending"
    }
  ]
}
```

### 去重语义（重要）
- 去重键：`approval_code`（数据库层有唯一索引兜底）。
- 重复拉取时**只更新**标题、申请人、申请时间、附件清单。
- **绝不覆盖** `task_status` 与 `write_status`。
  原因：若覆盖，一次误操作就会让已完成的审查全部重来，并可能触发重复回写。

### 异常
- `ApprovalGatewayError`：审批系统不可用。此时本地不产生任何新任务。

### 验收方式
连续调用两次，第二次应满足 `created == 0` 且 `updated == total`。

## 二、`get_contract_approval(instance_id)`

### 作用
查询单个审批单详情，同时同步附件清单到本地记录。

### 参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `instance_id` | str | 是 | 审批单业务唯一标识 |

### 返回（需求 2.4.3 要求的四部分）

```json
{
  "task_id": 4,                          // 本地任务主键，后续工具需要
  "approval_code": "HT-2024-0001",
  "approval_title": "数据治理平台采购合同",
  "applicant_name": "李静",
  "applied_at": "2026-10-22T09:15:00",
  "approval_status": "pending",          // 审批系统原始状态
  "task_status": "pending",              // 本地任务状态
  "write_status": "not_written",
  "blocked_reason": null,
  "blocked_detail": null,
  "form_data": { "申请部门": "技术中心", "金额": "1200000" },
  "attachments": [
    {
      "document_id": 4,
      "external_attachment_id": "ATT-0001",
      "file_name": "contract_normal.pdf",
      "file_type": "pdf",
      "file_size": 3586,
      "download_status": "pending",
      "file_path": "",
      "checksum": "",
      "download_error": null
    }
  ]
}
```

### 注意
- 附件记录在**下载前**就已创建（状态 `pending`）。这是需求 2.4.4「附件缺失进入 blocked」
  能够成立的前提——否则附件没下载时，系统连"缺了哪个附件"都不知道。
- `approval_status`（外部）与 `task_status`（本地）语义不同，**不做映射**。
  外部状态机由 OA 定义，强行映射会失真。

### 异常
- `NotFoundError`：该审批单尚未拉取到本地，或外部系统中不存在。
- `ApprovalGatewayError`：外部接口故障。

## 三、`download_contract_attachment(instance_id, attachment_id, file_name)`

### 作用
下载合同附件到本地受控目录，返回路径与校验信息。

### 参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `instance_id` | str | 是 | 审批单业务唯一标识 |
| `attachment_id` | str | 是 | **外部**附件编号（`external_attachment_id`） |
| `file_name` | str | 否 | 期望文件名；空则用审批系统记录的名字 |

### 返回

```json
{
  "document_id": 4,
  "task_id": 4,
  "file_name": "contract_normal.pdf",
  "file_type": "pdf",
  "file_size": 3586,
  "local_path": "D:\\...\\data\\attachments\\HT-2024-0001\\4_contract_normal.pdf",
  "checksum": "5c386f530b8ca0d94d7b531adc1bfe7614f5aefc3dbaa771febdfc0ceac029ec",
  "download_status": "success"
}
```

### 路径安全
文件名来自外部系统，属不可信输入。落盘前会：
1. 取 basename（剥离任何目录部分，含 Windows 与 POSIX 分隔符）；
2. 替换危险字符（保留中文、字母数字、`.`、`-`、括号）；
3. 截断过长主名但保留扩展名；
4. 校验最终路径仍在 `attachment_dir` 之下，越界则抛 `ValueError`。

### 异常
| 异常 | HTTP | 触发 | 后续动作 |
| --- | --- | --- | --- |
| `NotFoundError` | 404 | 审批单或附件记录不存在 | 检查参数 |
| `AttachmentMissingError` | 400 | 外部文件取不到 | 任务已置 blocked，补件后重试 |

### 副作用
- 文件写入 `data/attachments/{approval_code}/{document_id}_{safe_name}`。
- 附件记录更新为 `success`，写入 `file_size`/`checksum`/`file_path`。
- 失败时记录置为 `failed` 并写入 `download_error`。

## 四、`parse_contract_document(document_id)`

### 作用
解析单个附件，输出结构化字段与条款，每项带原文片段、位置、提取状态。

### 参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `document_id` | int | 是 | 本地附件主键（下载工具返回） |

### 返回

```json
{
  "document_id": 4,
  "task_id": 4,
  "parse_id": 1,
  "parse_status": "partial",     // success | partial | failed
  "basic_info": {
    "contract_no": {
      "label": "合同编号",
      "value": "HT-2024-0001",
      "snippet": "合同编号：HT-2024-0001",
      "location": "第1页第2行",
      "status": "success",       // success | failed | not_found
      "detail": ""
    },
    "effective_date": {
      "label": "生效时间",
      "value": null,
      "snippet": "",
      "location": "",
      "status": "not_found",
      "detail": "全文未找到日期标签…，也未匹配到语义表达"
    }
  },
  "clauses": {
    "confidentiality": {
      "label": "保密条款",
      "value": null,
      "snippet": "",
      "location": "",
      "status": "not_found",
      "detail": "未找到条款标题（保密/商业秘密/…），内容关键词也未命中"
    }
  },
  "meta": {
    "page_count": 1,
    "text_pages": [1],
    "ocr_pages": [],
    "char_count": 432,
    "elapsed_seconds": 0.036
  }
}
```

### 字段语义
- `basic_info` 固定 8 个键：`contract_title`、`contract_no`、`our_party`、
  `counterparty`、`amount`、`currency`、`effective_date`、`expire_date`。
- `clauses` 固定 8 个键：`payment`、`delivery`、`acceptance`、`breach`、
  `confidentiality`、`data`、`intellectual_property`、`dispute`。
- **一定返回全部键**，未检出的键状态为 `not_found` 且带 `detail` 说明。
  这样调用方无需处理"键缺失"这种额外分支。

### 关于 `status` 的三态
| 状态 | 含义 | 后续影响 |
| --- | --- | --- |
| `success` | 提取到值，且带位置 | — |
| `failed` | 定位到候选文本但解析不出（如大写金额） | 需人工确认 |
| `not_found` | 全文未找到 | 会驱动"缺失类"规则命中 |

**`not_found` 不等于"合同没写"**：它只表示"系统没检出"。
证据里写的是"未检出"，不是"不存在"——最终判断权在人工。

### 异常
| 异常 | 触发 | blocked_reason |
| --- | --- | --- |
| `AttachmentMissingError` | 未下载 / 本地文件丢失 | `attachment_missing` |
| `OcrUnavailableError` | 扫描件识别失败 | `ocr_unavailable` |
| `DocumentEmptyError` | 有效字符不足（含空白页） | `document_empty` |
| `UnsupportedDocumentError` | 格式不支持 | `unsupported_document` |

失败时**仍会写一条 `contract_parses` 记录**（`parse_status=failed` + `parse_error`），
满足需求 2.4.5「不允许只返回空结果」。

## 五、`run_contract_rules(case_id)`

### 作用
对任务执行全部启用规则，输出命中结果与风险结论。

### 参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `case_id` | int | 是 | 本地任务主键 |

### 返回

```json
{
  "case_id": 4,
  "overall_risk_level": "high",
  "evaluated_rule_count": 26,
  "hit_count": 5,
  "summary_text": "整体风险等级：高。本次共执行 26 条规则，命中 5 条…",
  "focus_points": [
    "[预付款比例过高] 建议将预付款比例压降至 30% 以内…"
  ],
  "hits": [
    {
      "hit_id": 1,
      "rule_id": 1,
      "rule_code": "R101_ADVANCE_PAYMENT_HIGH",
      "rule_name": "预付款比例过高",
      "risk_level": "high",
      "evidence_text": "检出数值 60%，触发条件 > 30%；原文：…",
      "evidence_position": "第1页第7行",
      "suggestion_text": "建议将预付款比例压降至 30% 以内…",
      "hit_status": "active"
    }
  ]
}
```

### 风险汇总规则
- 总风险等级 = 所有命中规则中的**最高**等级；无命中为 `low`。
- 命中列表按风险降序（高→中→低）。
- `evaluated_rule_count` 是"审查覆盖面"的唯一证据，**必须一并展示**——
  只报命中数会让人误以为"没命中 = 合同干净"。

### 重复调用
会先清空该任务的旧命中再重新写入（避免命中翻倍）。
清空范围严格限定在 `task_id`，不影响其他任务历史。

### 异常
- `NotFoundError`：任务不存在，或尚无解析记录（需先调解析工具）。

## 六、`save_review_result(case_id, overall_risk_level, summary_text, focus_points_json, comment_text)`

### 作用
保存审查结果，返回 `review_id` 供回写使用。

### 参数

| 参数 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `case_id` | int | 是 | 正整数 |
| `overall_risk_level` | str | 是 | `low` / `medium` / `high` |
| `summary_text` | str | 是 | 中文摘要 |
| `focus_points_json` | str | 是 | JSON **数组**字符串 |
| `comment_text` | str | 是 | 最终写入评论区的文本 |

### 返回

```json
{
  "review_id": 1,
  "task_id": 4,
  "overall_risk_level": "high",
  "focus_point_count": 5
}
```

### 关于重复保存
同一任务重复保存会**追加**新记录，并保留历史。
理由：审查结论属于审计材料，"上一次系统给的意见是什么"必须可回查。
读取侧统一取最新一条，因此累积历史不影响展示与回写。

### 异常
- `ValueError`：等级取值非法，或 `focus_points_json` 不是合法 JSON 数组。
- `NotFoundError`：任务不存在。

## 七、`write_approval_comment(instance_id, review_id)`

### 作用
把审查意见写入审批评论区。

### 参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `instance_id` | str | 是 | 审批单业务唯一标识 |
| `review_id` | int | 是 | 结果主键（保存工具返回） |

### 返回

```json
{
  "task_id": 4,
  "approval_code": "HT-2024-0001",
  "review_id": 1,
  "write_status": "success",
  "write_response_text": "评论已写入，当前评论数 1",
  "already_written": false
}
```

### 幂等保证（重要）
| 当前 `write_status` | 行为 |
| --- | --- |
| `not_written` | 正常写入 |
| `failed` | 正常写入（重试场景） |
| `success` | **不写入**，返回 `already_written=true` + 上次真实响应 |
| `writing` | **不写入**，抛 `TaskStateError`（有并发写在执行） |

实现方式：一条 `UPDATE ... WHERE write_status IN ('not_written','failed')` 完成
"检查 + 占位"，依赖数据库行级原子性，**跨进程有效**（不依赖进程内锁）。

### 异常
| 异常 | HTTP | 触发 | 后续动作 |
| --- | --- | --- | --- |
| `NotFoundError` | 404 | 审批单/结果不存在，或结果不属于该审批单 | 检查参数 |
| `TaskStateError` | 409 | 并发写入中，或任务非 blocked 时重试 | 稍后重试 |
| `CommentWriteError` | 400 | 超时 / 外部拒绝 | 任务已 blocked，`retry_target=reviewing` |

### 副作用
- `approval_tasks.write_status` 变更。
- 成功时任务置 `done`。
- 每次尝试写一条 `comment_logs`（成功与失败都记）。

## 八、典型调用链（完整闭环）

```python
import json
from app.tools import contract_tools

# ---- 1. 拉取待办（去重） ----
pull = contract_tools.list_pending_contract_approvals(limit=20)
assert pull["created"] >= 1

# ---- 2. 查详情（拿 case_id 与附件清单） ----
detail = contract_tools.get_contract_approval("HT-2024-0001")
case_id = detail["task_id"]

# ---- 3. 下载全部附件 ----
documents = []
for att in detail["attachments"]:
    dl = contract_tools.download_contract_attachment(
        instance_id="HT-2024-0001",
        attachment_id=att["external_attachment_id"],
        file_name=att["file_name"],
    )
    documents.append(dl["document_id"])

# ---- 4. 解析（单附件接口；多附件建议用编排函数合并） ----
parsed = contract_tools.parse_contract_document(documents[0])
print(parsed["basic_info"]["contract_no"]["value"])

# ---- 5. 规则审查 ----
review = contract_tools.run_contract_rules(case_id)
print(review["overall_risk_level"], review["hit_count"])

# ---- 6. 保存结果 ----
from app.services.result_service import build_comment_text
from app.services.parse_service import load_parse_outcome
from app.services.review_service import load_enabled_rules
from app.review.rule_engine import evaluate_rules

outcome = evaluate_rules(load_parse_outcome(case_id), load_enabled_rules())
comment_text = build_comment_text(
    detail["approval_title"], detail["approval_code"], outcome)

saved = contract_tools.save_review_result(
    case_id=case_id,
    overall_risk_level=review["overall_risk_level"],
    summary_text=review["summary_text"],
    focus_points_json=json.dumps(review["focus_points"], ensure_ascii=False),
    comment_text=comment_text,
)

# ---- 7. 回写 ----
written = contract_tools.write_approval_comment(
    instance_id="HT-2024-0001", review_id=saved["review_id"])
print(written["write_status"], written["already_written"])
```

**多附件场景**建议直接用编排函数，它会自动合并所有附件的字段与原文：

```python
result = contract_tools.run_full_pipeline(case_id)
# result["attachments"] 下载明细
# result["parse"]       合并后的解析结果
# result["review"]      审查结论 + review_id + comment_text
```

## 九、错误处理建议

```python
from app.domain.errors import (
    NotFoundError, TaskStateError, ContractReviewError,
)

try:
    contract_tools.run_full_pipeline(case_id)
except NotFoundError:
    # 404：对象不存在，检查 instance_id / case_id 是否传错
    ...
except TaskStateError:
    # 409：状态冲突（并发写、对非 blocked 任务重试），稍后重试
    ...
except ContractReviewError as exc:
    # 400：业务规则不满足
    # exc.reason 可用于分支处理，例如：
    #   attachment_missing  → 提示补件
    #   ocr_unavailable     → 提示换清晰扫描件
    #   document_empty      → 提示检查文件
    #   unsupported_document→ 提示转换格式
    #   comment_write_failed→ 重试回写（不必重新解析）
    print(exc.reason, exc.message, exc.retry_target)
```

**重试入口**：

```python
# 状态复位（只改状态，不执行）
info = contract_tools.task_service.retry_blocked_task(case_id)

# 复位 + 按 retry_target 自动续跑
result = contract_tools.retry_task(case_id)
```

## 十、调用约束速查

| 约束 | 说明 |
| --- | --- |
| 顺序 | 下载前必须先拉取（否则无 `document_id`）；解析前必须已下载；审查前必须已解析 |
| 去重 | `approval_code` 唯一；重复拉取不新建任务、不重置状态 |
| 幂等 | 回写重复调用不会重复写外部系统 |
| 并发 | 同一任务同时只允许一个回写；同一任务同时只允许一个运行中任务（由状态机保证） |
| 重处理 | 已 `done` 的任务默认拒绝重新解析；确需重审时显式传 `allow_reprocess=True` |
| 不代替人工 | 所有输出都是"风险提示"与"关注点"，不含通过/驳回结论 |

### 关于 `allow_reprocess`

已回写成功（`task_status=done`）的任务再次调用
`parse_task_documents(case_id)` 或 `run_full_pipeline(case_id)` 时，
会抛 `TaskStateError` 拒绝。

原因有两条：

1. **状态可信**：`done` 表示"意见已送达审批人"。若允许静默重跑，
   状态会退回 `parsing`，页面上看起来"已完成的任务又被打开了"，
   审批人会怀疑之前那条意见是否作废。
2. **成本**：扫描件 OCR 每页约 5 秒，一次误触就白花一次。

若合同换版、确实需要重新审查，显式放行：

```python
contract_tools.run_full_pipeline(case_id, allow_reprocess=True)
# 或只重跑解析
contract_tools.parse_service.parse_task_documents(case_id, allow_reprocess=True)
```
