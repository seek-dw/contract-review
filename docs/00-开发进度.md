**迁移过程中处理的两个问题**：

1. **`requirements.txt` 写成了 Python docstring 风格**。
   原来文件开头是 `"""合同审批审查系统运行依赖。"""`，pip 只认 `#` 注释，
   直接报 `Invalid requirement`。已改为 `#` 注释格式。
   这是交付可用性的问题——收到项目的人第一条命令就会失败，必须修。
2. **RapidOCR 1.4.4 的返回结构有变化**：置信度从字符串变成 float。
   `parser/ocr.py` 本来就写了 `float(item[2])`，两种类型都能处理，
   因此无需改代码。为确认这点，我实测了 1.4.4 的原始返回并跑了全量测试。

## 五、开发中修复的 10 个真实缺陷

每个都有对应的回归测试，详见 `README.md` 第九节。摘要：

1. 标签子串匹配导致签约主体抽成正文句
2. 金额格式化为科学计数法 `1.2e+06`
3. 日期只认显式标签，漏"有效期至"表述
4. 空文档误报 `ocr_unavailable`（应为 `document_empty`）
5. 合并解析记录丢失原文行，全文检索失效
6. 审查读取错误记录，多附件时误报"条款缺失"
7. **并发回写未互斥**：`writing` 状态可被覆盖，导致重复写外部系统
8. 审批单不存在时抛错类型不当（应为 404 而非接口故障）
9. 状态无变化仍打日志，产生 `reviewing → reviewing` 噪声
10. 测试配置隔离失败：重载模块导致"建表成功但表不存在"

## 六、已知局限

见 `README.md` 第十节。要点：

1. 字段抽取基于正则与版式假设，排版差异大的合同需补充模式；
   失败会如实标记，**不伪造字段值**。
2. OCR 对手写体、印章遮挡、低分辨率扫描件识别率下降，识别不足时进 blocked 交人工。
3. threshold 规则抽不到数值时**不命中**（避免假风险）。
4. 真实 OA 只提供 HTTP 网关骨架，厂商字段映射需按对接文档补充。
5. 未实现登录与权限（需求未要求）。
6. 规则维护仅只读页面。
7. mock 网关的 JSON 写入未加文件锁，多进程并发演示需换真实系统。
